# Channels

A channel is a two-way connection between a chat transport (Telegram, Slack, …) and an agent. Where a [trigger](/concepts/triggers) is one-way (it fires an event and forgets), a channel accepts inbound messages from the **transport** and uses a **conversation** handle to relay the answer back.

Built-in channels:

- Telegram: `telegramChannel`

Use `serve` to bind an agent to a channel:

```ts
import { serve, telegramChannel } from 'roboport/channels';

const bot = serve(
  agent,
  telegramChannel({ token: process.env.TELEGRAM_TOKEN }),
);
// later: await bot.stop();
```

## Transports

Channels support two transports.

By default, polling is used. Zero config, ideal for local development.

You can also use webhooks, which are recommended in production:

```ts
const channel = telegramChannel({
  token: process.env.TELEGRAM_TOKEN,
  transport: {
    mode: 'webhook',
    secretToken: process.env.TELEGRAM_WEBHOOK_SECRET,
  },
});
const bot = serve(agent, channel);

const route = '/webhooks/telegram';
app.post(route, (c) => bot.handle(c.req.raw));
await channel.client.setWebhook(`${publicUrl}${route}`, {
  secretToken: process.env.TELEGRAM_WEBHOOK_SECRET,
  allowedUpdates: ['message'],
});
```

## Inbound messages

Each inbound message is provider-agnostic data:

```ts
interface InboundMessage {
  id: string; // transport message id, for replies and dedup
  conversationId: string; // stable session key (e.g. chat id)
  text: string;
  user?: { id: string; name?: string };
  replyTo?: ReplyContext;
  raw?: unknown; // narrowed by the channel (Telegram: `TelegramMessage`)
}
```

When the user replies to an earlier message, `replyTo` carries that message, not just a pointer to it — Telegram ships the parent inline with the update, so there is nothing to look up:

```ts
interface ReplyContext {
  id: string;
  text?: string;
  user?: { id: string; name?: string };
  isBot?: boolean; // the agent's own message, rather than a human's
  quote?: string; // the fragment the sender highlighted, if they picked one
}
```

`text` is filled in even when the parent was a rich message. Those carry no `text` of their own — the content is a block tree — so it is flattened back to plain text, which matters because replying to one of the agent's own replies is the common case.

By default `serve` prompts the agent with `message.text` alone, so a reply reaches the model with no idea what it points at. Use the `prompt` seam to fold the context in:

```ts
serve(agent, channel, {
  prompt: (message) => {
    const quoted = message.replyTo?.quote ?? message.replyTo?.text;
    if (!quoted) return message.text;
    const from = message.replyTo?.isBot ? 'assistant' : 'user';
    return `<replying-to from="${from}">\n${quoted}\n</replying-to>\n\n${message.text}`;
  },
});
```

Whatever `prompt` returns is what gets persisted to the conversation store, so the transcript records what the model actually saw.

## Custom channel

A channel implements the `Channel` interface: `open(handler)` wires the transport and returns an unsubscribe (mirroring a trigger's `start`), `handle?(req)` is present for webhook transports the host mounts in an HTTP server, and `relay?` sets the default reply strategy. Each inbound message arrives with a `Conversation` carrying `send(text)` and an optional `thinking()` presence indicator. `telegramChannel` is the reference implementation.
